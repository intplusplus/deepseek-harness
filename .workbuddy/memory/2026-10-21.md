## 重试接进驱动层（本轮）

- `dsh-agent-loop` 的 `run_step` 从「一次请求」改成 attempt 循环；`recover_request` 是 TS `agent/request-error` 恢复点的 Rust 对应物：无策略/无该 provider 策略/预算耗尽 → 以 failure 结束 turn；有策略 → 先 append `llm/retry`（**先落盘再等待**），`delay.wait()` 返回 false → `TurnEndReason::Aborted{User}`，true → append `llm/retry-started`，同 step 重试（每步重新 `derive_messages`，重试看到与失败attempt 相同的上下文）。
- **`DEFAULT_MAX_ATTEMPTS = 8`**：always 策略本身无界，offline 驱动需要自己的天花板，超界以 code `ATTEMPT_LIMIT` 结束（与 `DEFAULT_MAX_STEPS`/`STEP_LIMIT` 同思路）。
- **抓到的真实缺陷（三态而非两态）**：最初 `run_attempt` 把「重试」和「工具调用后开新 step」都返回 `Ok(None)`，`run_step` 的重试循环把后者误判为重试 → 整个 turn 挤在第一个 step 里（`a_tool_call_opens_another_step` 报 steps=1 而非 2）。修为 `StepAttempt{Retry, Continue, Ended}` 三态 enum。**教训：两个「还没完」的语义一旦塌成一个 `None`，循环就会静默吞掉边界；重试循环与步进循环的交汇点必须用判别联合。**
- 测试修正两处（测试自身的错，非代码）：`fold_retry_state` 折叠**整个**日志时 `turn/end` 会清空状态（正确行为，step 作用域）→ 改为折叠到 `llm/retry` 事件处的前缀；`flaky_provider(1,..)` 跨 turn 只失败一次 → 改为「每个 turn 的第一次请求失败」（按 request.messages.len() 去重）。
- `dsh_session::write_session(directory, session)` / `read_session(directory)` 收的都是**目录**（内部选最高 generation），不是文件路径。
- 当前测试数：agent-loop 23（turn 11 + recovery 12）；非 dsh-tools 的 crate 全绿 91 + agent-loop 23 = 114。

## system-prompt 层（子 agent 移植）+ gate 层审查结论

- `dsh-system-prompt`（新 crate，`packages/core/system-prompt`）：54 个测试全绿（assembly 19 / scoped 18 / tool_order 6 + 11 个库内单测），clippy 零警告，`cargo run -p dsh` 不受影响。
- **未依赖 dsh-session**：本 crate 不贡献 `SessionEventMap` 成员（两个 Cordis 事件都是易失插件事件），所以没有 Extension encode/decode 对 —— 与 dsh-retry 相反。
- **注册是 RAII**：`Registration` guard drop 时精确移除自己加的东西；provider 是注入闭包（`Fn(&AssembleContext) -> ..`），注册表内部不碰时钟/文件系统/随机源。
- **两套集合语义刻意区分**：variables **活迭代**（复刻 TS live Map 迭代器 + detach 规则），tool providers **快照**（成员在任何 provider 运行前冻结）。
- **顺序不能漂移**：section `(order, 码元名称)`、context order、tool 配置序 + `TOOL_ORDER_REST` 收容未列出者；排序稳定，同名 tool 保持注册序，section/context 并列回落名称比较。
- **自己抓到的缺陷**：`Registration::drop` 里 `Rc::upgrade()` 会 panic（guard 自身持 `Weak`，LIFO 降级顺序下触发 `BorrowMutError`，升级顺序不报 → 潜伏缺陷）。修法：**drop 里不 upgrade**，`Weak` 只判"注册表是否还活着"。
- **教训**：Rust 类型只要含 `Box<dyn Fn>` / `Rc<dyn Fn>` 就无法 `#[derive(Debug)]`，链式断在整个 derive 上 → 给这些类型**手写 Debug**（Rc 内层字段逐个 fmt，不要整体 `{:?}`）。
- 当前 rust/ 测试总数 **216**（agent 4 / llm 12 / plugin 8 / session 19 / tools 48 / system-prompt 54 / agent-loop 23 / retry 48）。

## 线格式：preserve_order 打开后暴露的两处真实分歧（本轮自查）

- 工作区根 `Cargo.toml` 打开 `serde_json` 的 `preserve_order` —— 打开后 216 个测试仍全绿，**说明此前没有任何测试保护过字段顺序**。
- **v4 信封是扁平的**：TS 的 `sessionFormatCatalog.encodeCurrentEvent` 一路恒等（`session-format-v3-to-v4/src/codec.ts:46` → `session-format-v1-to-v2/src/codec.ts:36` 的 `encodeSourceEventRanges`），所以当前格式就是 `{"type":"turn/start","turn":1}`，Rust 结构正确。`{"type","seq","time","data"}` 嵌套信封只是 **v0** 格式（`session-persistence-jsonl/tests/fixtures/released-v0-real-shapes.jsonl` 是唯一现成 fixture，不能直接用于 v4 对拍）。
- **分歧 1（已修）**：`ExtensionEvent::new` 原来 `insert` 追加 `type`，标签排在所有字段之后；TS 每一行都以 `type:` 开头（所有格式测试字面量都是 `{ type: '...', ... }`）。修为前置（先 `remove` 再建新 map）。往返测试对此完全不敏感，只有字节级对拍能发现。
- **分歧 2（已修）**：`LlmRetryEvent` 的 `#[serde(tag = "mode")]` 把 `mode` 顶到最前，而 TS 声明序（`packages/llm/llm-retry/src/types.ts:16-40`）是 `retryId, turn, step, provider, mode, policyKey, retry, maxRetries, delayMs, failure` —— `mode` 是**第五**个键。修为手写 `Serialize`（`serialize_map` 按序输出），`Deserialize` 保持 derive（读标签与顺序无关）。`LlmRetryStartedEvent` 顺序本就一致，无需改。
- **新增 4 个字节级测试**：retry 三个（normal / always / started 的精确 JSON 字符串）+ session 一个（`type` 前置且声明序不被排序）。rust/ 测试总数 **220**。
- **方法论**：`preserve_order` 这类"让隐藏属性变可观测"的开关，打开后第一件事应该是**补回归测试**，而不是只跑一遍看有没有挂 —— 全绿只说明"没人依赖旧行为"，不说明"新行为被保护"。
